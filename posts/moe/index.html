十分钟看懂 MoE（混合专家模型）：从 FFN 到路由、负载均衡与跨设备通信

用 8 专家、Top-2 的最小例子，把 MoE 的路由机制、参数与计算量为什么能解耦、以及负载不均与跨设备通信两个代价讲清楚。附 7 张示意图。

MoE（Mixture of Experts，混合专家模型）听起来很唬人，但它的出发点只有一句话：把一个很大的 FFN 拆成很多小份，每次只让其中一部分上场。

这篇文章用一个「8 个专家 + Top-2」的最小例子，把 MoE 的路由机制、参数量与计算量为什么能解耦、以及它的两个典型代价讲清楚。

一、一句话概括

把一个参数量很大的 FFN 拆成许多小份（每个小份叫一个「专家」），每次运行时只挑中其中一部分专家参与计算。

这样一来，模型的总参数可以做得很大（能力上限更高），但每个 token 实际激活的参数（计算量）仍然可控。

二、为什么从 FFN 开始讲？

MoE 的改造对象是 Transformer 块里的 FFN：

Transformer Block = Attention + FFN
  • Attention 负责 token 之间的信息交互；
  • FFN（前馈网络）负责把 Attention 的输出转换成这一层最终的隐状态。

MoE 的改造思路非常朴素：

  1. 把一个完整的 FFN「分」成若干份，比如分成 8 份；
  2. 每一份都称为一个专家（Expert），于是就有了 Expert 1 ~ Expert 8；
  3. 再在它们前面加一个 Router（路由 / 门控网络），由它决定每个 token 该交给哪些专家。

关键点：专家在结构上就是 FFN，它们之间没有本质区别，区别只在于训练中各自学到的擅长方向不同。

三、MoE 的基本计算流程（单个 Token）

以输入 token t0 为例，本例中专家数为 8、k = 2。

1. Router 打分

用一个参数矩阵 Wr 与 t0 做运算，得到一个 1 × 8 的得分向量 O：

       E1   E2   E3   E4   E5   E6   E7   E8
O   = [ 1    4    2    5    0    3    2    1 ]

每个格子代表 t0 对该专家的「匹配度」得分。

2. Top-k 选择

取分数最高的 k 个专家。这里 k = 2，得分最高的是 E4（5 分） 与 E2（4 分），因此 t0 被路由到 Expert 4 和 Expert 2。其余 6 位本轮完全不参与。

3. Softmax 求权重

对选中的这 2 个分数做 Softmax，得到归一化的权重：

E4 = exp(5) / (exp(5) + exp(4)) ≈ 0.731
E2 = exp(4) / (exp(5) + exp(4)) ≈ 0.269

未选中的专家权重为 0，两者之和恒为 1。

4. 专家计算 + 加权求和

                              ┌─→ Expert 4 (FFN) ─→ out₄ ─× 0.731 ─┐
t₀ ─→ Router ─→ Top-2 ────────┤                                     ├─→ Σ ─→ h₀
                              └─→ Expert 2 (FFN) ─→ out₂ ─× 0.269 ─┘

两个专家的输出分别乘以各自权重，再相加，就得到 t0 在这一层的最终输出 h₀。

5. 流程小结

Router → Top-k → 选中的 FFN 做运算 → 结果加权后相加 → h

这就是 MoE 最基本的计算逻辑。

四、扩展到多个 Token：从向量到矩阵

当一次输入有多个 token（记为 t₀ … t₇）时，流程完全一致，只是所有张量都升了一维：得分从 1 × 8 的向量变成 8 × 8 的矩阵，每一行对应一个 token 对 8 位专家的打分。

对每一行各自做 Top-2 选择，再对选中的两个分数做 Softmax，就得到该 token 的权重。本例的完整结果如下：

Token得分最高的两位权重
t₀E2（5）、E4（3）0.881 / 0.119
t₁E5（5）、E7（3）0.881 / 0.119
t₂E2（5）、E8（3）0.881 / 0.119
t₃E6（5）、E2（3）0.881 / 0.119
t₄E5（5）、E2（3）0.881 / 0.119
t₅E7（5）、E3（3）0.881 / 0.119
t₆E2（5）、E6（3）0.881 / 0.119
t₇E1（5）、E2（3）0.881 / 0.119

本例把每行的最高分与次高分都设为 5 与 3，所以权重恒为 0.881 / 0.119；这也便于观察后面那个「负载不均」的问题。

分发之后，各专家之间可以完全并行计算。 算完后按同样的方式把每个 token 的结果加权合并，得到这一层的最终输出 H。

这就是多个 token 时的处理过程，也是 MoE 能提高吞吐的原因：专家维度天然可并行。

五、MoE 的优点：参数量与计算量解耦

用一组具体数字对比一下。

稠密 FFNMoE（8 专家，k=2）
结构单个 FFN8 个专家，各 200M
FFN 总参数1600M1600M
激活参数 / token1600M400M
每个 token 的计算全部参数参与只激活 2 位专家

结论：

  • MoE 的总参数与稠密版持平（都是 1600M），模型容量没有缩水；
  • 但每个 token 的激活参数只有 400M，仅为总量的 25%，因为只有 2 位专家被选中；
  • 于是同时拿到两边的优点：模型容量按稠密版对齐，而单 token 的算力开销接近一个小模型。

这里只用了 8 位专家差距就已经很明显。实际应用中动辄几十到几百位专家，总参数与激活参数之间的鸿沟会更加夸张，MoE 的收益也就更加突出。

六、MoE 的两个典型缺点

缺点 1：负载不均（Load Imbalance）

还是 8 位专家、8 个 token、k = 2，把上面的分发结果按专家统计一下：

专家收到的 token数量
Expert 1t₇1
Expert 2t₀ t₂ t₃ t₄ t₆ t₇6
Expert 3t₅1
Expert 4t₀1
Expert 5t₁ t₄2
Expert 6t₃ t₆2
Expert 7t₁ t₅2
Expert 8t₂1

8 个 token、k = 2，一共只有 16 个「专家槽位」，却分成了 6 / 2 / 2 / 2 / 1 / 1 / 1 / 1：Expert 2 一个吃掉 6 个，而 Expert 1、3、4、8 各自只被点到一次，极差达到 5。

后果是双向的：

  • 训练时：冷门专家很少被选中 → 拿不到足够梯度 → 欠训练；
  • 推理时：总是那几位在干活，其余大量闲置 → 参数被浪费。

所以，想让 MoE 真正发挥优点，就必须解决负载不均衡问题。

缺点 2：跨设备通信复杂度

MoE 的专家通常不会全放在一张卡上，而是要分布到不同 GPU 上。就以 8 位专家分到 4 张卡为例：

设备专家处理 token 数
GPU 1Expert 1、Expert 28（全部）
GPU 2Expert 3、Expert 42
GPU 3Expert 5、Expert 64
GPU 4Expert 7、Expert 83

一旦专家分散在多卡上：

  1. token 被路由到不同 GPU → 设备之间需要通信（分发 / All-to-All）；
  2. 专家算完之后 → 还要把结果跨设备重新聚合回来。

于是两个问题会叠在一起：

  • 通信量随被选中的专家数增长，专家越多、切分越细，跨卡往返越频繁；
  • 负载不均会被多卡进一步放大 —— GPU 1 承载了 Expert 1 与 Expert 2，要处理全部 8 个 token，成为瓶颈，而其他卡在等它，整体吞吐被最慢的一张卡拖住。

如何设计一套高效的调度与通信算法，把这些设备充分利用起来，是 MoE 落地时最难的工程问题之一。

七、总结

核心思想

把一个参数量很大的 FFN 拆成许多小份，每次运行只选中的部分专家去运行。

收益

  • 模型容量可以按稠密版对齐（本例总参数 1600M）；
  • 同时把激活参数压到 25%（本例 400M），计算量不随总参数膨胀；
  • 专家可并行，吞吐友好。

代价

  • 需要解决专家之间的负载不均衡；
  • 专家变多后，专家之间相互通信的复杂度显著上升。

八、下一步

负载均衡与通信开销是 MoE 绕不开的两道坎，也是所有 MoE 大模型工程实现的核心议题。接下来值得深入看的是 DeepSeek 系列是如何处理这两个问题的——包括它的专家粒度设计、偏置式负载均衡策略，以及通信与计算的重叠。
